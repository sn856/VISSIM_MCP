# Engineering notes — things that bite if you do not know them

COM behaviour observed while building this server on PTV Vissim 2026 (SP09). After a Vissim version change, re-check with `tools/com_probe.py`.

## Vissim COM — connection and lifetime

- **A Vissim started with `Dispatch` lives as long as the process that started it.** It is a COM server, so it closes when the last reference (our process) goes away. That is why the server is a resident process (tray) whose lifetime is separate from the AI client session: the session can end while Vissim and the open network stay.
- **You cannot attach to a Vissim the user started in the GUI.** Neither a Vissim started with `Dispatch` nor one started with `Vissim260.exe -automation` appears in the Running Object Table (ROT) within 120 s (`GetActiveObject` → `MK_E_UNAVAILABLE`). A second check of `-automation` alone: `GetActiveObject` every 5 s for 90 s, all `-2147221021` (`MK_E_UNAVAILABLE`), and no Vissim entry in the ROT at start. Registering the `Dispatch` object in the ROT from a helper process with `pythoncom.RegisterActiveObject` is refused with `E_INVALIDARG` (IUnknown and IDispatch, strong and weak). Adding `-automation` to a shortcut does not help.
- With the server running and an `-automation` Vissim (empty window) started 30 s earlier, `open_network` did not use that window; it started another Vissim (`launched=true`, warning "1 Vissim besides the server's"). Neither `Dispatch` nor `GetActiveObject` picks up a window you started yourself. So "always controllable from chat" is solved by routing every open through the server, not by attaching ([adr/0003](adr/0003-launcher-through-server.md)).
- **Another reason not to use `GetActiveObject`**: re-acquiring the running Vissim from the ROT on each request sometimes fails on timing, and `Dispatch` then starts a new instance instead (an earlier tray bridge started three within 35 s). The server starts its own instance with `vissim_com.launch` (Dispatch only) and keeps it. The server Vissim's PID is the difference between `tasklist` `Vissim*.exe` lists taken before and after launch (if the difference is not exactly one, pid is unknown and a warning is added).
- **Call `tasklist` with `CREATE_NO_WINDOW`.** The server runs under console-less `pythonw`; calling a console program without that flag flashes a console window each time.
- **If `tasklist` fails**, the server cannot tell whether another Vissim is running, so it assumes one is (`other_vissim_processes = null`; saving needs `force`).
- **One process can drive two Vissims**: two `Dispatch` calls in one process and one thread gave two instances, each with its own file; alternating reads and writes did not mix. Releasing the reference closed each within seconds. Each window uses a licence, and with one COM thread a busy window blocks the other. The server stays at one Vissim by design.

## Vissim COM — threads and retries

- **Symptom**: touching a COM object from another thread gives odd attribute errors such as `AttributeError: <unknown>.Graphics` → **Cause**: COM apartment rules — only the creating thread may use the object → **Fix**: every COM call goes through the queue of one `ComThread`. Restoring per-thread proxies through the Global Interface Table (GIT) also works, but a server that serializes calls anyway is simpler with one dedicated thread.
- **Symptom**: while Vissim is busy (modal dialog, loading) COM calls fail with `-2147418111` (`RPC_E_CALL_REJECTED`, "call was rejected by callee") → **Fix**: `ComThread` retries only that error, `com_retry_count` times (default 5) every `com_retry_interval_s` (0.5 s), then reports `com_error`. It does not retry forever.
- **No reconnect loop after Vissim closes.** Polling Vissim for status piles up hundreds of errors a day when it is closed or busy, and then needs reconnect, back-off and cool-down machinery. The server keeps state in memory and detects loss from the next command's COM failure, reported once.
- `pywin32` COM objects are `callable()` (default member call). Code that does "call it if it is a function" fails on a COM object with `-2147352573` ("member not found"). Use `isinstance(val, types.FunctionType)`.

## Vissim COM — objects and attributes

- **Symptom**: `Net.DesSpeedDistributions` → `AttributeError: <unknown>.DesSpeedDistributions` → **Cause**: the 2026 container is `Net.SpeedDistributions` (the official example script uses a name that does not exist) → **Fix**: trust probe output over docs and examples.
- **Symptom**: `link.Attributes` / `lane.Attributes` / `v.Evaluation.Attributes` → `<unknown>.Attributes` → **Cause**: in 2026 the attribute list exists only on **containers** → **Fix**: `describe_attributes` uses the container (`Links[n].Lanes` etc.); single objects return `not_found` and point to `attribute.xlsx` in the Vissim install. Metadata fields: `ID` (upper case), `Code` (real name), `Name`, `ValueType`, `Editable`, `Category`.
- The first `set_attributes` write of `DesSpeedDistr(10)` returns `before` = `None` (class not assigned) and `after` = the string `'5'`. Compare values as strings.
- Do not pick a desired speed distribution number at random for demand or speed tests. The first distribution in a network may be `5 km/h`, so vehicles crawl and travel time measurements can show 0 vehicles. Look at names with `list_objects("DesSpeedDistribution")` (e.g. `100 km/h`).
- Registry create signatures were copied from the official example script and then all confirmed on 2026 SP09 by `tools/com_probe.py --net <saved .inpx>` (`verified=True`). After a version change, re-run it. Do not replace a rejected signature with a guess.
- `ReducedSpeedArea` `Decel` and `DesSpeedDistr` need a vehicle-class sub-attribute to be read (`Decel` alone is rejected). Class numbers differ per network, so they are not in the default attributes; read them as `attrs`, e.g. `"Decel(10)"`.

## Simulation and results

- **Chunked run**: `SimBreakAt = t + chunk` → `RunContinuous()` (returns at the break) → read `SimSec`. Calling `RunSingleStep` per step means tens of thousands of COM round trips for a one-hour simulation plus a full redraw each time; it looks like the network keeps reloading. If `SimSec` is missing or does not advance, the loop ends on the computed value (no infinite loop). After the run, `QuickMode` is restored to its previous value.
- When a simulation runs to the end, `SimSec` goes back to 0. `SimulationRuns.Count` grows by one per run (`Current` in results is the last run).
- **Symptom**: on an empty new network (`New()`, never saved) `RunContinuous()` does not return (over 10 min) → **Cause**: Vissim opens a modal save dialog to choose the result folder, and COM blocks → **Fix**: run simulations only on networks opened from a file. `tools/com_probe.py` skips simulation and result items without `--net`.
- Evaluation groups have no `…WriteFile` attribute (only raw data `…RawWriteFile`). `configure_evaluation`'s `write_file` only adds a warning. With only `…CollectData` on, aggregated results come **only through COM result attributes (`get_results`)**; `<name>.results\` gets just the result DB, no `.att`. `.att` files exist only when the user exports result lists in Vissim or turns on raw data output → `read_result_file` is for those.
- **A time interval out of range** is not `None` but a COM error `The subattribute no. 2 '3' of type 'Time Interval' … does not match` → `get_results(interval="all")` treats that error as the end of intervals and stops (if the first interval already fails, the error is raised).

## Parking

- **Symptom**: `ParkRate(1)` = `50.0` → `Value 5000 % exceeds value range of attribute Parking rate (Max: 100 %)` → **Cause**: percentage attributes take 0–1 over COM → **Fix**: `park_rate` is taken as 0–1 (0.5 = 50 %) and not converted. Result metrics `OccupRate`, `ParkSpcBlockRate`, `ParkReqDeclShare` use the same scale.
- **Symptom**: `AddParkingLot` on a 0.84 m link → `Length per space is less than the minimum value 1` → **Cause**: the lot needs room for a space length (`LenPerSpc`) of at least 1 m → **Fix**: put lots on aisle links that are long enough.
- A new lot has `Type=REALPARKINGSPACE`; `Length` 20 m → `Capacity` 3 (default `LenPerSpc`). The parking space container `ParkSpcs` is keyed by `Index` (from 1).
- Building floors (link `Level`, connector ramps) and automatic space layout (Car park creator) are out of scope. Links and connectors are protected, and Car park creator has no method in the COM type library. Draw them in Vissim, then handle lots, decisions and evaluation through MCP.
- The 2026 single object `Evaluation` has no `Attributes`. Read evaluation attributes one by one by ID, e.g. `AttValue("DataCollCollectData")`.
- Time distributions: container `Net.TimeDistributions`; writing `Mean` and `StdDev` of a normal distribution works. Empirical distributions may not have `Mean`/`StdDev`, so the default attributes are `No` and `Name` only.

## View and capture

- `Screenshot` is on `Graphics.CurrentNetworkWindow`, not on `IGraphics` (`Graphics.Screenshot` → `<unknown>.Screenshot`). `Screenshot(path, 1)` writes a PNG the size of the editor area.
- 3D toggle: `NetworkWindow.SetAttValue("3D", 1)`. Camera: `SetCameraPositionAndAngle(x, y, z, yaw, pitch)` (yaw 90 = looking north, pitch = angle looking down).
- Showing background images and 3D models and switching the online map are **not in COM**. `INetworkWindow` members are only `AttValue`, `SetAttValue`, `GetCoordinates`, `SetCoordinates`, `Screenshot`, `ZoomTo`, `ApplyLayout`, `SetCameraPositionAndAngle`, `SetCameraPositionAndFieldOfView` (listed with `_oleobj_.GetTypeInfo()`); there is no `ShowMap` window attribute and no `GraphicParameters`. Visibility changes only through `Vissim.LoadLayout(.layx)` — so `set_view(layout="view")` loads a copy with four display attributes changed ([adr/0002](adr/0002-view-layout-and-capture.md)). `NetworkWindow.ApplyLayout(path)` is refused with "no layout named …" (it is for named layouts).
- A `.layx` holds several network editor layouts (default, smart map, the real editor window — `paneLayoutNo`), so all are changed. With the online map (`showMap`) on, Vissim downloads map tiles from an external server every time the network opens. Vissim does not rewrite the `.layx` when it opens and exits.
- **Use whole-window capture for development checks.** When another tool clicks the Vissim window, an on-screen overlay window can swallow clicks on the network object pane and menus. `capture_view(mode="window")` captures the server's Vissim window with Win32 `PrintWindow(PW_RENDERFULLCONTENT)`, including 3D and even when covered. A 3D scene takes a few seconds to draw, so the capture waits `capture_settle_s` (3 s).
- **Object locking is not in COM.** The lock in the network object pane ("Toggle selectability in current network editor") works per object **type**, not per object, and blocks selection and editing in that editor. The COM type library (`Vissim260.exe`, 1,192 interfaces, 19,401 members) and `attribute.xlsx` have no lock or selectability method or attribute. The only ways to lock:
  - Click the lock with a real mouse (background clicks and UI Automation value writes report success but change nothing).
  - Edit the `.layx` and load it with `Vissim.LoadLayout`. Locking adds only `<unselectableTypes><typeRef id="BACKGROUNDIMAGE"/></unselectableTypes>` inside the relevant `<networkEditorLayout>` of the saved `.layx`; the `.inpx` stays byte-identical. Loading that `.layx` into a network opened over COM locked background images only.
  - Reading the lock state works in the background through UI Automation: the `<type name>_editable` cell of the network object pane (`True` = unlocked, `False` = locked).
  - `set_view` does not do this: it changes only the four display attributes. Other types' `typeRef id` values and their effect were not checked.

## Server process

- **The official `mcp` package is 2.x**: 1.x `FastMCP` became `mcp.server.mcpserver.MCPServer`; HTTP transport is `run_streamable_http_async(host, port, streamable_http_path)` / `streamable_http_app()`. In-memory tests use `mcp.client.client.Client(mcp)`. Tool functions are `async def`, and blocking work goes through `anyio.to_thread.run_sync` (registering a sync function directly can block the event loop).
- **Symptom**: two tray icons → **Cause**: the HTTP thread died (first because `pythonw` has `stdout=None`) while the tray main thread lived on, leaving a ghost process without a server; a newly started server took the port, giving two icons → **Fix**: if the HTTP thread ends or raises, the whole process exits (`_serve_http_or_die`), and at start a named mutex (`Local\vissim_mcp_server`) allows only one server process (on top of the port check). To find a leftover ghost: `tasklist /FI "IMAGENAME eq pythonw.exe"`, then `taskkill /PID <pid> /F`.
- **Three threads**: tray (`pystray` takes the main thread — `icon.run()` blocks; menu callbacks run on another thread), HTTP (`asyncio.run` on a secondary thread), COM (dedicated). `python -m vissim_mcp` starts `pythonw.exe -m vissim_mcp --serve` with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` and returns (no console window). Shutdown is `request_quit` → release COM references → `os._exit(0)`; ending the process proved more reliable than a graceful HTTP shutdown.
- **Quit dialog** uses `ctypes.windll.user32.MessageBoxTimeoutW` (message box with timeout; return 32000 = timed out). It can be called from the tray callback thread or the HTTP thread.
- **Do not tell Vissim windows apart by title.** The server's Vissim and the user's windows all read "PTV Vissim 2026". Before closing one, check which process opened which `.inpx`: `Get-CimInstance Win32_Process -Filter "Name like 'Vissim%'" | Select ProcessId, CommandLine`. `vissim_status.vissim.pid` may differ from the real `Vissim260.exe` PID, and if the server's Vissim is closed from outside, `running: true` remains until the next command detects the loss. Compare with the process list.
- **`taskkill /T` (without `/F`) does not close Vissim.** Vissim 2026 runs a `msedgewebview2.exe` child with six children of its own. `taskkill /PID <main> /T` cannot deliver a close message to the windowless webview children (or they demand `/F`), and while children live the parents refuse to exit. `Get-Process -Id <main> | % { $_.CloseMainWindow() }` closed it within 10 s and the webview children went with it. Not tested: the save prompt when the model has unsaved changes.

## Double-click launcher and following the open file ([adr/0003](adr/0003-launcher-through-server.md))

- The full path of the open file is `AttValue("WorkingFolder")` (ends with `\`) + `AttValue("InputFile")` on the Vissim **top-level object**. `Net.AttValue("InputFile")` does not exist. An empty Vissim has `InputFile=''` and `WorkingFolder` = the Vissim exe folder.
- `LoadNet` discards unsaved changes without a dialog. That is why `open_network` and the launcher ask for confirmation whenever a file is open or content is drawn, whatever the write count.
- A recovery copy (`SaveNetAs`) makes the copy the file open in Vissim. If an open-file check ran after that, the server would follow the copy as "a file opened from the menu" → the shutdown procedure makes the recovery copy last (just before exit), inside the lock.
- The shutdown procedure holds `Runtime.lock` through the dialogs (up to `quit_prompt_timeout_s`) and the save. Tools and `/admin/*` (including the launcher's status check) wait meanwhile. During a long tool call the launcher may show "server busy" (Retry/Cancel).
- The launcher's "opening" window is tkinter. Removing the system menu to hide the close button also removes the title bar icon (the taskbar icon stays). tkinter objects must be destroyed on the thread that created them (destroying them from another thread ended the process with exit code 3).
- "No server" vs "server busy" in the launcher: if the port is free, it starts the server at once without asking (a refused connection on a closed port takes about 2 s). If the port is in use but `/admin/status` times out, it is "busy" (Retry/Cancel, no plain-Vissim button).
- **Commands started inside the Claude desktop app (a packaged Store-style app) have HKCU and `%LOCALAPPDATA%` writes redirected to app-private storage.** Icons and `install.json` written by `install` ended up under `%LOCALAPPDATA%\Packages\Claude_<id>\LocalCache\Local\…`, and the registry association went into an app-private hive, invisible to Explorer (the shortcut icon showed a blank document; `.inpx` kept the Vissim icon and action). The desktop and Startup folders were written in the real location. `GetCurrentPackageFullName` fails in that process, so it cannot detect the case → `install` writes a test file to `%LOCALAPPDATA%` and checks whether it lands in `Packages\*\LocalCache\Local\`; if so, it writes the same command to a `.cmd` and hands it to `explorer.exe`, whose child runs outside the app and writes to the real location (output in a temporary log, end marker `EXIT=<code>`). In a `.cmd`, `echo EXIT=%errorlevel%>> file` breaks because `EXIT=0>>` is parsed as redirecting handle 0 → write `>> file echo EXIT=…`. A double-click test with `cmd /c start` inside the app also saw the virtualized association, so it is not a real Explorer double-click test.
- `.ico` files are written in the native Windows format (directory entry count 1, PNG for 256, the rest 32-bit bitmaps with doubled height plus AND mask). Pillow's ICO writer leaves the count at 0 and no AND mask; `LoadImage` reads it, but Explorer compatibility is not guaranteed (the shortcut icon showed as a blank document). Icon file names carry a content hash, because the icon cache remembers paths and keeps showing the old picture otherwise.
- Tray: `pystray` loads the icon at 32 px and scales it down, which blurs it → the tray icon is drawn at tray-slot size (`SM_CXSMICON`) and loaded directly.
- The `.inpx` file icon is `HKCU\Software\Classes\<ProgID>\DefaultIcon` (overrides HKLM); double-click is the `shell` default value under the same key. If the user picked "Always use this app" in Windows (`FileExts\.inpx\UserChoice`), that wins. Shortcuts (`.lnk`) are created with PowerShell `WScript.Shell`, so the package does not import `win32com` for that.

## Vissim COM — scenarios, signals, time intervals (probe)

Checked on Vissim 2026 (SP09) with the extra option group of `tools/com_probe.py`. Official examples were copied first; the probe opened and saved only per-run copies (the originals' checksums were unchanged). Signal timelines are `SigState` read after stopping every second with `SimBreakAt = 1, 2, …` (the state that just changed in that second is read — green command at 2000 ms → `GREEN` at 2 s).

**Scenario management**
- `v.ScenarioManagement` is available only in scenario management mode. Otherwise: `Internal error in CCOMVissim::get_ScenarioManagement: Not in scenario management mode.` — usable to detect the mode (`NetPara.UnderScenMngm` is also 1 for scenarios, 0 otherwise).
- `LoadProject(<full path of .vissimpdb>)`, `LoadScenario(n)` and `LoadModification(n)` (Python ints) are all accepted.
- Open file (top-level `WorkingFolder` + `InputFile`): `WorkingFolder` is always the project folder (ends with `\`). `InputFile` is:
  - after `LoadProject`, `LoadBaseNet`, `LoadModification(n)`: the base network name as is (e.g. `Intersection Layout.inpx`) — **base and modifications cannot be told apart by path**.
  - after `LoadScenario(n)`: `<PROJECT.PROJECTNAME> - <SCENARIO.NAME>.dummyExtension`. It differs per scenario but uses the **name, not the number**, and no such file exists on disk. Map the name to a number through the `SCENARIO` table of the `.vissimpdb`.
- `.vissimpdb` (SQLite) tables: `PROJECT(PROJECTNAME, CURRENTUSER, CURRENTMACHINE, NO)`, `SCENARIO(NO, NAME, DESCRIPTION, MODIFICATIONS "1,3", SCENTOCOMP)`, `MODIFICATION(NO, LOADINDEX, NAME, DESCRIPTION, GROUP, EXCLUSIONS, DEPENDON)`, `LOGENTRY(NO, DATE, ENTRY)`, plus `MAXKEY` and `UPDATECOUNTER`. Just opening writes the `.vissimpdb` (same size, `CURRENTUSER` and `CURRENTMACHINE` filled) and `Temp\CacheAfterLastForScenario.inpx`, `CacheBeforeLastForScenario.inpx`, `CacheForModification.inpx`.
- Files changed by the save methods (after changing only the first vehicle input `Volume(1)`):
  - `SaveScenario()`: the scenario's **last modification** (`MODIFICATIONS "1,3"` → `Modifications\M000003.trax`).
  - `SaveScenarioAs("<name>")`: returns `int` 4 (new scenario number). New modification `M000004.trax` (443 B), plus `SCENARIO (4, '<name>', '', '1,3,4', '2,3')`, `MODIFICATION 4`, `LOGENTRY 'Modification 4 has been created.'`. The open file becomes `… - <name>.dummyExtension`.
  - `SaveInMultipleScenarios("1,2")`: takes a comma string (BSTR in the type library). Creates `M000005.trax` and appends 5 to the `MODIFICATIONS` of scenarios 1 and 2 (`'1,3,5'`, `'5'`); reopening shows the new value in both.
  - `SaveModification()` (after `LoadModification(1)`): `M000001.trax`.
  - All four also **rewrite `<name>.layx` in the project folder** and update `Temp\Cache*.inpx`. The base `.inpx` and `Scenarios\` were unchanged (no simulation).
- `SaveNetAs(<copy>.inpx, False)` with a scenario open: accepted. The open file becomes the copy, but `UnderScenMngm` stays 1, the project folder does not change, and the copy folder gets `.inpx` and `.layx`. That `.inpx` contains `underScenMngm="true"`, so **`LoadNet` refuses it** (`The network file could not be loaded.`, Vissim is left empty). `LoadProject` + `LoadScenario(1)` reopens the original (changed value kept).
- `PlaceUnderScenarioManagement("<project>", "<scenario 1>")` on a plain `.inpx` copy: accepted. In the same folder it creates a `.vissimpdb` **named after the `.inpx`** (not the project), folders `Backups\`, `Modifications\` (empty), `Scenarios\S000001\`, `Temp\` (`CacheAfterLastForScenario.inpx`), and **rewrites the `.inpx` (302,870 → 302,644 B) and `.layx` in place**. Tables: `PROJECT '<project>'`, `SCENARIO (1, '<scenario 1>', '', '', '')`, no `MODIFICATION`. Open file `<project> - <scenario 1>.dummyExtension`.

**Model transfer files (`.trax`)**
- `GenerateModelTransferFile(NetPath, out, Reverse, False)`, `GenerateModelTransferFileBetweenFiles(base, target, out, False)` and `ApplyModelTransferFile(path)` are all accepted; the open file (`base.inpx`) does not change.
- Direction, with the open network = base and `NetPath` = variant: `Reverse=False` is **variant → base** (new links `<deleted>`, names back to the original `<modified>`); `Reverse=True` is base → variant (same file as `BetweenFiles(base, variant)`). Applied to base, the `Reverse=False` file changes nothing; the `Reverse=True` / `BetweenFiles` files changed links 13 → 15, connectors 20 → 21, link 1 `Name` → `'probe A'`, and for the reference point file `RefPointMapX` 257.1235 → 357.1235.
- Shape: under `<network version="1403" vissimVersion="2026.00-09 [307071]">`, each object group (`<links>`, `<netPara>` …) has `<added>` (full elements), `<deleted>` (`<link no="10120"/>`) and `<modified>` (changed attributes only, `<link name="probe A" no="1"/>`). Connectors are `<link>` inside `<links>` too (`<fromLinkEndPt link="10120" pos="100"/>`, `<lanes><lane><fromLanes><objectRef key="10120 1"/>` … `<toLinkEndPt …/>`). A moved poly point is `<link no="10119"><geometry><modified><linkPolyPts><overwritten>` (full point list) `</overwritten>…`. Reference point: `<netPara><modified><refPointMap><modified x="357.1235"/></refPointMap></modified></netPara>`. A Vissim 8 example `.trax` has `version="201"`.
- `ApplyModelTransferFile` can change links, connectors and the reference point — a single COM call that bypasses the MCP protected list. The server does not expose it.

**Signals (FIXEDTIME = VISSIG, FIXEDTIMESIMPLE)**
- `IntSupplyData` is a base64 string (decoded: `<?xml …?>\r\n<sc version="201503" id="1" … checkSum="1078716222">`, 5,780 B). For FIXEDTIMESIMPLE, `AttValue` returns `None`.
- Mapping (FIXEDTIME): `<cmd display="3" begin="G">` → **green from G s**, red-amber (`fixedstate display="2"`, 1 s) just before it (G−1). `<cmd display="1" begin="R">` → **red from R s**, amber (`display="4"`, 3 s) before it (R−3). Measured SG 3: cmd 2000/14000 → `REDAMBER@1 GREEN@2 AMBER@11 RED@14`, cycle 60 s (`REDAMBER@61 GREEN@62`). Actual green = [G, R − amber).
- FIXEDTIME SG writes to `EndRed`, `EndGreen`, `Amber`, `RedAmber` are **rejected**: `AttValue failed: Object 1 - 3: East entry: Attribute End of red cannot be changed.` (same for `End of green`, `Amber`, `Red-amber time`). Reads: `EndRed`/`EndGreen` 0.0, `Amber` 3.0, `RedAmber` 1.0. Timeline unchanged.
- FIXEDTIME SC `CycTm` write is **rejected** (`Attribute Cycle time cannot be changed.`; reads 0.0, `CycTmIsVar` 1). `Offset` 10 is accepted and reads back 10.0, but neither `IntSupplyData` nor the timeline (80 s) changed — **no effect**. `ProgNo` 2 (a program the example does not have) is accepted and reads back 2, but the simulation does not start (`The simulation could not be continued.`).
- Changing one cmd in `IntSupplyData` (SG 3 `display="1" begin="14000"` → `19000`), keeping all other bytes and the `checkSum`, and writing it back as base64 is **accepted**. The value read back equals the bytes written; `checkSum` is not recomputed (1078716222 unchanged). Timeline `AMBER@16 RED@19` — it takes effect.
- Creating: `SignalControllers.AddSignalController(0)` → No 2 (max + 1), `Type` default `FIXEDTIME`, `IntSupplyData` **empty string** (still empty after adding groups and after `SaveNetAs` → `LoadNet`; there is no `<progs />` to fill). `SC.SGs.AddSignalGroup(0)` → No 1, 2 (from 1 per controller), `Amber` and `RedAmber` 0. `SignalHeads.AddSignalHead(0, <lane object>, 10.0)` accepted. Head ↔ group attribute `SG` is the string `"<SC>-<SG>"` (e.g. `'1-9'`; lane `Lane` is `'1-2'` too). A new head's `SG` defaults to `'1-3'` (first group of the first SC); `SetAttValue("SG", "2-1")` accepted.
- First program of a new SC: writing a **full document** taken from the example SC, with only `<sc … id>`, the group definitions `<sgs><sg id=…>`, `<progs>` (one program) and `<stages>` (→ `<stages />`) renumbered, as base64 is accepted (`checkSum` left at the example value). `ProgNo` 1; simulation gives `SG 2-1: REDAMBER@1 GREEN@2 AMBER@12 RED@15`, `SG 2-2: … GREEN@22 AMBER@32 RED@35` — it works.
- `RemoveSignalController(<SC object>)`: SC 2 → 1, and its groups **and the heads bound to them are removed too** (heads 9 → 8, `ItemKeyExists` False).
- FIXEDTIMESIMPLE (`CycTm` 72): SG writes to `EndRed`, `EndGreen`, `Amber` are accepted and take effect. Meaning differs from VISSIG: `EndRed`=5 → `REDAMBER@5 GREEN@6` (end of red = start of red-amber; green = `EndRed` + `RedAmber`), `EndGreen`=50 → `AMBER@50 RED@53` (end of green = start of amber). `EndRed` 7, `EndGreen` 55, `Amber` 4 → `REDAMBER@7 GREEN@8 AMBER@55 RED@59`.

**Time intervals and vehicle compositions**
- `TimeIntervalSets` keys are ints. An empty new network has 1–9 and 11 (one interval, `Start` 0, `End` 1.797e308) and 100–121 and 200 (0–3600 plus two more of 3600; 106 and 200 have seven of 600 s). A set has only `No` and `ExistsInScen` — **no attribute says which object type uses it**. Number mapping from the official example comments: 1 vehicle inputs, 2 static routes, 3 partial routes, 4 parking routes, 5 pedestrian inputs, 6 pedestrian partial routes, 7 PT partial routes, 8 area behaviour, 9 managed lanes, 11 pedestrian static routes. 100 and above not checked.
- Interval attributes: `Index` (read), `Start` (write), `End` (read), `TmIntSet`, `ExistsInScen`. `TimeInts.AddTimeInterval(0)` appends; `Index` = count, `Start` default = previous + 900 (900, 1800). `SetAttValue("Start", 900)` accepted. `RemoveTimeInterval(<interval object>)` accepted — later intervals' `Index` shift down (sub-attribute `Volume(2)` then points to the old third interval).
- Existing vehicle input values for a new interval: `Volume(n)`, `VehComp(n)`, `VolType(n)` **copy the previous interval** (600 → 600; set the previous to 1200 before adding and it is 1200), `Cont(n)` = 1 (continued). While `Cont` is 1, writing `Volume(n)` is rejected: `AttValue failed: Object 1: Attribute Volume (900-MAX) cannot be changed.` → write `SetAttValue("Cont(2)", False)` first. Static route `RelFlow(2)` also copies the previous value (0.7). Sub-attribute n is the interval `Index`.
- `VehCompRelFlows`: no `ItemByKey` (`<unknown>.ItemByKey` — by vehicle type number or by index). Only `GetAll()` and `Count`; item attributes `VehType` (string `'100'`), `DesSpeedDistr` (`'5'`), `RelFlow`, `VehComp`. `AddVehicleCompositionRelativeFlow(<vehicle type>, <speed distribution>)` and `RemoveVehicleCompositionRelativeFlow(<item>)` accepted. **A container reference taken before adding does not update `Count`** (stays 1; a fresh `comp.VehCompRelFlows.Count` is 2) — fetch it again each time. (`TimeInts` references did update.)
- `Net.SimulationRuns`: `GetMultiAttValues("No")` → `((1, 1), (2, 2), (3, 3))`; `GetMultipleAttributes(["No", "Timestamp", "RandSeed", "SimEnd"])` → `((1, '2026-10-19 03:11:52', 42, 65.0), …)`; `GetAll()` + `AttValue("No")` gives the same. These numbers go in the run slot of result sub-attributes: `TravTm(2,Total,All)` and `DelayAvg(3,Total,All)` accepted; `Current` = last, `Avg` = average. A run number that did not collect that evaluation fails with `The subattribute no. 1 '1' of type 'Simulation Run' of the attribute 'TRAVTM(1,TOTAL,ALL)' is invalid: Object 1 does not match`. The example's `KeepPrevResults` is `KEEPNONE` (only the last previous run is kept); `SetAttValue("KeepPrevResults", "KEEPALL")` accepted.

## Prior art

A public Vissim MCP server exists: `XIEXIANG924/vissim-mcp` (MIT; FastMCP over stdio, about 25 tools, a fake backend with a four-intersection demo network and a COM backend). No code was reused. Its COM backend differs from this design in ways that matter here: it attaches to a running Vissim with `GetActiveObject`; it has no protection on saves or attribute writes; it captures a screen region with `pyautogui` (other windows get captured); it finds objects by position (`Item(i)`) instead of number; it does not pin COM calls to one thread. Two ideas worth noting: MCP resources that expose state by address (`vissim://project/info` etc.) and a `zoom_to` tool that moves the view to an object (links have no X/Y attributes, so this needs the geometry).

## Python and environment

- Python 3.12 (64-bit). Install in editable mode (`pip install -e ".[dev]"`) so `python -m vissim_mcp` works from any folder. Re-run it after adding a package.
- `pyproject.toml` sets `[tool.pytest.ini_options] pythonpath = ["src"]`, so pytest runs without installing. Tests do not need Vissim.
- Non-ASCII output can look garbled in a Windows console with a legacy code page. The log files (UTF-8) are authoritative.
